# zhanhBlueB 制作与修复复盘

## 项目边界

zhanhBlueB 是 Android 10 以上与 Windows 11 x64 之间的离线互传工具。两端通过已配对的 Bluetooth Classic RFCOMM 连接，不依赖网络、账号或服务端。Android 使用 Kotlin、Jetpack Compose，Windows 使用 C#、.NET 10 和 WPF；协议采用版本化消息、长度分帧、流式文件块和 SHA-256 完成校验。

## 制作经验

- 先把协议核心从平台 UI 和蓝牙驱动中分离，使用跨语言 golden 样本、拆包/粘包测试和管道双进程测试，能在没有真机时验证编码、状态机和大文件流式传输。
- 文件接收先写临时文件，完成后校验 SHA-256，再用安全文件名和同名重命名落盘；不要把整个文件读入内存，也不要把未经校验的临时路径显示成可打开文件。
- 剪贴板图片统一转 PNG，并用本地写入标记、消息编号和暂停开关阻止收到内容再次回传。Android 只在应用获得焦点时读取剪贴板，手机发送保持手动，避免依赖 Root、Shizuku 或输入法。
- 把系统配对、RFCOMM 链路安全、应用首次信任和设备地址绑定分成四个门。任何一层失败都应有中文提示、超时清理和可重试路径。
- 验收按层分开：核心单测、协议异常、跨语言管道、WPF 离屏界面、正式包完整性、真实蓝牙和真机权限。自动化通过不等于 vivo X300 或所有 Android API 的真机通过。

## 修复经验

### 1. RFCOMM 连接被错误拒绝

现象是系统已配对、Windows 却提示没有通过认证与加密检查。根因是 32feet.NET 3.5 接收端 client 的 `Authenticate` / `Encrypt` getter 只是初始化为 false 的包装缓存，并不查询实际链路状态。旧代码把这个缓存当成事实，因而在发送 HELLO 和应用信任确认前关闭了连接。

修复保留监听 socket 对认证和加密的强制设置、系统配对检查和双方应用信任，只移除错误的接收 wrapper 缓存判断。这个判断不能反向证明链路不安全；监听端的原生安全策略和操作系统拒绝机制才是边界。修复后增加已配对缓存为 false、未配对设备、安全设置失败三类回归测试。

### 2. 图片发送后无法双击打开

旧记录没有保存接收文件最终路径，也没有为 Windows 剪贴板图片生成可打开的本地副本。修复让完成记录保存 `SavedPath`，普通文件使用发送源路径，收到的文件使用实际重名后的最终路径；剪贴板 PNG 采用临时文件、PNG 和 SHA-256 校验后保存。WPF 双击事件只处理左键、已完成记录，并通过 `ProcessStartInfo` 的 `UseShellExecute=true` 和 `Verb=open` 调用默认程序，避免 shell 拼接。文件被移动、删除、没有默认应用或额外副本保存失败时只提示，不把传输错误误报成发送失败。

### 3. 安卓接收后需要去下载目录找文件

Android 1.0.1 将系统 MediaStore 返回的实际 URI 和最终文件名写入接收记录，而不是按发送端
文件名重新拼接路径。这样同名重命名后的记录仍指向正确副本。点击“打开”通过系统选择器
授予临时只读权限；Android 11 以上还需要声明对应 `ACTION_VIEW` 包可见性查询，才能可靠
检查是否有匹配应用。未知类型或无具体匹配时回退通用 MIME，并在启动前检查文件是否可读。

历史写入和文件传输分别处理：下载文件完成校验、保存成功后即为接收成功；之后历史写入失败
不能让对端收到失败确认，也不能抹去当前打开入口。100 条记录由版本化 JSON 和 AtomicFile
串行保存，裁剪只移除元数据。选择器、跨应用读取授权和 Compose 点击测试需要设备；
JVM 覆盖率只证明历史、MIME 和记录合并的纯逻辑。操作和边界见 [安卓文件打开](android-file-opening.md)。

### 4. Windows 传输记录需要可控的文件清理

右键菜单从 `PlacementTarget` 取得记录编号，在点击时重新查找当前记录；这样右键非选中项、菜单弹出后列表变化时不会操作另一条记录。路径优先使用接收后的 `SavedPath`，其次使用发送源 `Source`；删除发送原文件的确认框显示完整路径和原文件说明，默认取消。

“删除记录”只移除元数据；“删除记录与本地文件”使用 Shell `IFileOperation` 的强制回收选项，在独立 STA 线程执行并核对回收结果，不执行永久删除降级。回收期间按规范化路径加锁，阻止同路径发送及重复删除；相关记录保留传输结果并标记本地文件已移除。删除记录后清理图片重试缓存并忽略迟到进度。

记录显示完成后仍可能有接收回调和任务清理，新增本地 `ReceiveSettled` 回调在资源释放前保持 `JobPending`，避免过早回收正在收尾的文件。协议帧不变。平台测试只使用独立临时文件验证回收、恢复和占用失败，不接触用户文件。

## 验证与限制

WPF 离屏测试曾因调度器触发真实 `App.OnStartup` 而启动产品逻辑，出现旧实例提示或等待。
测试宿主改用 `App(startProduct:false)`，注入文件启动器和临时下载目录，验证界面事件时
不接触真实剪贴板、不开启蓝牙，也不启动外部图片应用。

构建过程还遇到本机 Python 3.10 访问冲突及控制台编码错误，切换已有 Python 运行时后
跨语言测试通过；部分 .NET 命令独立重跑后成功。这里只记录现象和恢复步骤，
没有确认这些间歇失败的底层原因。遇到工具失败应保留返回码，不能据一次失败改写产品结论。

Windows 1.0.3 核心 44 项、蓝牙 8 项、桌面 43 项测试通过，核心行覆盖率 97.31%，新增记录操作 96.42%、记录状态 83.33%；WPF 菜单、非选中项操作、临时文件真实回收与恢复检查通过。Android 1.0.1 核心 29 项测试、应用 JVM 4 项测试通过；核心行覆盖率 99.64%、分支 83.46%，新增历史/MIME 与记录合并纯逻辑行覆盖率 100%。跨语言 100 MiB 双向传输和协议异常 14 项独立回归通过。完整 verify.ps1 本次仍曾遇到子进程异常退出和编码错误；分项通过不等于完整脚本单次通过。ReadyToRun 的 crossgen2 两次异常退出后，Windows 1.0.3 改用成功的标准自包含发布。尚未由本机自动化证明 vivo X300 真机、Android API 29/31/33/36 的真实权限弹窗、系统选择器及外部应用读取、真实射频吞吐、系统默认图片查看器、后台省电策略和磁盘不足等场景；这些边界必须在发布说明中保留。

## 可复用原则

1. 先确认底层 API 的语义和实现，再相信状态 getter；缓存值不能自动代表系统状态。
2. 每个用户可见动作都记录可验证的最终资源路径和状态，传输状态与本地附加保存状态分离。
3. 用分层探针和分项证据解释“连接成功”“文件已保存”“文件可打开”，不要用一个 UI 或进程现象代替完整验收。
4. 公开源码前清除签名私钥、机器路径、缓存和大体积构建产物；第三方库按原许可证保留通知，不能把项目许可证覆盖到第三方二进制。

首次开源准备中，源码 ZIP 与 Git 文件清单比对发现 `TestResults` 下的覆盖率报告仍被
打包脚本收录，尽管 Git 已忽略它。补齐打包与发布校验的排除规则，并确认两份文件清单和
源码字节一致后再上传。`.gitignore` 只控制 Git，不会自动约束独立的归档脚本。

## 后续修改与发布经验

- 系统打开能力应复用平台接口：Android 保存实际 URI、临时授权并弹出选择器，Windows 保存最终路径并调用默认程序。应用负责定位资源和解释失败，无需为每种文件内置查看器。
- 文件传输成功、历史保存成功、文件仍然存在、任务清理完成是不同状态。打开和删除入口应分别检查这些状态；附加操作失败不能倒退已完成的传输结果。
- 记录操作以传输编号定位，以规范化路径协调文件访问。删除一条记录与回收一个共享文件的影响不同，需要处理其他记录、重试缓存和迟到回调。
- 维护原有公开仓库和发布历史，分别标明 Windows 与 Android 版本。安卓沿用原签名支持覆盖安装；私钥只保留在本机，安装包通过 Release 资产分发。
- 文档更新后重新归档，即使 APK 和 EXE 未变，ZIP 的哈希也可能变化。发布前比对源码清单和字节、校验包，上传后核对远端提交、标签、资产大小和 SHA-256；保留实际发布证据。
