# zhanhBlueB 制作与修复复盘

## 项目边界

zhanhBlueB 是 Android 10 以上与 Windows 11 x64 之间的离线互传工具。两端通过已配对的 Bluetooth Classic RFCOMM 连接，不依赖网络、账号或服务端。Android 使用 Kotlin、Jetpack Compose，Windows 使用 C#、.NET 10 和 WPF；协议采用版本化消息、长度分帧、流式文件块和 SHA-256 完成校验。

## 制作经验

- 先把协议核心从平台 UI 和蓝牙驱动中分离，使用跨语言 golden 样本、拆包/粘包测试和管道双进程测试，能在没有真机时验证编码、状态机和大文件流式传输。
- 文件接收先写临时文件，完成后校验 SHA-256，再用安全文件名和同名重命名落盘；不要把整个文件读入内存，也不要把未经校验的临时路径显示成可打开文件。
- 剪贴板图片统一转 PNG，并用本地写入标记、消息编号和暂停开关阻止收到内容再次回传。Android 只在应用获得焦点时读取剪贴板，手机发送保持手动，避免依赖 Root、Shizuku 或输入法。
- 把系统配对、RFCOMM 链路安全、应用首次信任和设备地址绑定分成四个门。任何一层失败都应有中文提示、超时清理和可重试路径。
- 验收按层分开：核心单测、协议异常、跨语言管道、WPF 离屏界面、正式包完整性、真实蓝牙和真机权限。自动化通过不等于 vivo X300 或所有 Android API 的真机通过。

## 修复经验

### 1. RFCOMM 连接被错误拒绝

现象是系统已配对、Windows 却提示没有通过认证与加密检查。根因是 32feet.NET 3.5 接收端 client 的 `Authenticate` / `Encrypt` getter 只是初始化为 false 的包装缓存，并不查询实际链路状态。旧代码把这个缓存当成事实，因而在发送 HELLO 和应用信任确认前关闭了连接。

修复保留监听 socket 对认证和加密的强制设置、系统配对检查和双方应用信任，只移除错误的接收 wrapper 缓存判断。这个判断不能反向证明链路不安全；监听端的原生安全策略和操作系统拒绝机制才是边界。修复后增加已配对缓存为 false、未配对设备、安全设置失败三类回归测试。

### 2. 图片发送后无法双击打开

旧记录没有保存接收文件最终路径，也没有为 Windows 剪贴板图片生成可打开的本地副本。修复让完成记录保存 `SavedPath`，普通文件使用发送源路径，收到的文件使用实际重名后的最终路径；剪贴板 PNG 采用临时文件、PNG 和 SHA-256 校验后保存。WPF 双击事件只处理左键、已完成记录，并通过 `ProcessStartInfo` 的 `UseShellExecute=true` 和 `Verb=open` 调用默认程序，避免 shell 拼接。文件被移动、删除、没有默认应用或额外副本保存失败时只提示，不把传输错误误报成发送失败。

## 验证与限制

WPF 离屏测试曾因调度器触发真实 `App.OnStartup` 而启动产品逻辑，出现旧实例提示或等待。
测试宿主改用 `App(startProduct:false)`，注入文件启动器和临时下载目录，验证界面事件时
不接触真实剪贴板、不开启蓝牙，也不启动外部图片应用。

构建过程还遇到本机 Python 3.10 访问冲突及控制台编码错误，切换已有 Python 运行时后
跨语言测试通过；部分 .NET 命令独立重跑后成功。这里只记录现象和恢复步骤，
没有确认这些间歇失败的底层原因。遇到工具失败应保留返回码，不能据一次失败改写产品结论。

当前自动化验证覆盖 Windows 核心 97.26% 行、85.39% 分支，Android 核心 99.53% 行、83.38% 分支，桌面打开/PNG 保存 23 项，跨语言 100 MiB 双向传输，协议异常 14 项，WPF 离屏双击事件和正式包完整性。尚未由本机自动化证明 vivo X300 真机、Android API 29/31/33/36 的真实权限弹窗、真实射频吞吐、系统默认图片查看器、后台省电策略和磁盘不足等场景；这些边界必须在发布说明中保留。

## 可复用原则

1. 先确认底层 API 的语义和实现，再相信状态 getter；缓存值不能自动代表系统状态。
2. 每个用户可见动作都记录可验证的最终资源路径和状态，传输状态与本地附加保存状态分离。
3. 用分层探针和分项证据解释“连接成功”“文件已保存”“文件可打开”，不要用一个 UI 或进程现象代替完整验收。
4. 公开源码前清除签名私钥、机器路径、缓存和大体积构建产物；第三方库按原许可证保留通知，不能把项目许可证覆盖到第三方二进制。

首次开源准备中，源码 ZIP 与 Git 文件清单比对发现 `TestResults` 下的覆盖率报告仍被
打包脚本收录，尽管 Git 已忽略它。补齐打包与发布校验的排除规则，并确认两份文件清单和
源码字节一致后再上传。`.gitignore` 只控制 Git，不会自动约束独立的归档脚本。
